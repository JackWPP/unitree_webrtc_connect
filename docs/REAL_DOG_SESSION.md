## 1. 探针 —— 全场最重要的一条命令（2 分钟）

**先做这个。** 它决定后面能做什么，而且它是只读的，不会占用控制权。

```sh
.venv/bin/python scripts/probe_webrtc_topics.py \
    --ip 192.168.31.188 --sn B42N6000Q3UC1M8C
```

会打印一张 13 行的表。**上次的结果**：`lowstate` / `multiplestate` 应答，
**`rt/sportmodestate` 静默 8 秒**（站起来之后也一样）。

这次要特别看三行：

| 行 | 有数据意味着 | 静默意味着 |
|---|---|---|
| `rt/lf/sportmodestate` | **步态/模式有了** —— 控制台现在能显示它 | 维持现状：控制台不显示步态，且**不假装** |
| `rt/utlidar/robot_pose` | **绝对位姿有了** —— 可以做真实地图和编队 | 「在哪」只能到"位移+朝向" |
| `rt/mapping/grid_map` | 可以做占用栅格图 | 不做 |

`--json` 出机器可读的版本，**原样带回来**。

> **看到静默不要当成故障。** 固件就是不在 WebRTC 上发它。这是本项目的核心
> 纪律：**没有第二条路拿到数据之前，不在静默的行上建功能。**

## 2. 单狗接管（5 分钟）

**先准备 roster。** 控制台不知道狗在哪，必须先告诉它 —— 而且**两只狗的 roster
要一起写好**，第 5 步就不用再回头改：

### 直接可以用的一份

`/tmp/fleet-demo/real-duo.json` 已经生成好了（0600），可以直接：

```sh
export UNITREE_AGENT_ROSTER=/tmp/fleet-demo/real-duo.json
```

内容：

| | dog1 | dog2 |
|---|---|---|
| 序列号 | `B42N6000Q3UC1M8C` | **`B42D1000P4J7JC08`** |
| 别名 | Go2_58174 | Go2_31437 |
| IP | `192.168.31.188` | **待填** |
| 密钥 | 有（内联） | **不需要** |

### 关于这两只狗最重要的一件事：**它们是不同世代的固件**

用云端账号查出来的，不是猜的：

```
B42N6000Q3UC1M8C  dev.key 有值   → 固件 ≥ 1.1.15，data2=3，要每机密钥
B42D1000P4J7JC08  dev.key 为空   → 固件 < 1.1.15，data2=2 或明文，不要密钥
```

**这直接就是你说的"两只狗不一样"的一个具体来源。** 预期会看到：

- **dog2 可能发布 dog1 不发布的 topic**，反之亦然 —— 上次会话里
  `rt/sportmodestate` 在 dog1 上是静默的，dog2 上不一定
- **能力差异会在控制台里显示出来**（感知页的数据来源清单是**每狗一份**的）
- 所以第 1 步的探针**要两只都跑**，报告里也是每狗一张表

**如果 dog2 连不上**：先跑 `--preflight` 看它卡在哪一步。密钥那一步不该拦它。

### 自己写一份

```sh
cat > /tmp/dogs.json <<'JSON'
{
  "default": "dog1",
  "state_dir": "/tmp/unitree-console",
  "robots": [
    {"id": "dog1", "model": "Go2", "ip": "192.168.31.188",
     "sn": "B42N6000Q3UC1M8C", "aes_128_key": "<32位十六进制>"},
    {"id": "dog2", "model": "Go2", "sn": "B42D1000P4J7JC08"}
  ]
}
JSON
chmod 600 /tmp/dogs.json
```

**注意 dog1 的密钥要内联**（`aes_128_key`），而不是指望密钥文件 ——
密钥文件在 `state_dir/dog1/keys.json`，换一个 `state_dir` 就找不到了。
上次会话能连上就是因为当时那份 roster 把它内联了。

### 不知道 IP 的时候

```sh
.venv/bin/python scripts/find_dogs.py --email <账号> --password <密码> --region cn
```

它会**同时**试三条路：多播、扫本网段、查账号设备列表，然后打印一份
**可以直接粘贴的 roster**。上面那两只狗的序列号就是这么来的。

然后**只读体检**（不占用狗的 WebRTC 槽位，可以放心跑）：

```sh
.venv/bin/python -m unitree_fleet_web.cli --preflight
```

预期每只狗一行 `[OK]`。上次的真实输出长这样：

```
[OK]   dog1     Go2  192.168.31.188   ready, data2=3
```

不通的时候它会**说清楚是哪一步不通**：

```
[FAIL] dog1     Go2  192.168.31.188   unreachable
         no answer on 9991 or 8081
         → Neither signaling port answered. Check the robot is powered on and
           on this network, and that no firewall is blocking 9991/8081.
```

起控制台：

```sh
.venv/bin/python -m unitree_fleet_web.cli --port 8080 --log-level INFO 2>&1 | tee /tmp/console.log
# 浏览器打开 http://127.0.0.1:8080
```

点狗卡片上的「连接」。预期：

- **视频**：1280×720，约 4 fps，真切画面
- **电量条**：94–98%，32 V 左右
- **本体条带**：姿态气泡居中、四根足端柱、`速度 0.00 m/s　指令 0.00`
- **感知页的数据来源清单**：`电量/IMU/足端`、`音量/亮度/避障开关` 亮**有数据**

**如果步态那一行是「未应答」** —— 那是已知情况（探针第 1 步会确认），不是坏了。

## 3. 驾驶 —— 站立闸门第一次上真机（10 分钟）

这是本轮改动里**最需要真机验证**的一条。

**先让狗趴下**（姿态页点「趴下」），等它趴稳。然后**按 W**。

预期看到驱动状态依次是：

```
空闲  →  等待站立…  →  行驶中
```

**「等待站立…」是关键。** 它意味着控制台发现狗没站好，**先发了一条站立命令，
并且没有下发速度**。上真机之前它只会是：按 W，什么都不发生，也没有解释。

要确认的：

1. 「等待站立…」大约持续多久才变成「行驶中」？（真机大概 1–2 秒）
2. 狗**站起来之后**才走，还是**一边起身一边走**？后者是 bug。
3. 直接对已经站着的狗按 W，**不该**出现「等待站立…」。

再试**停不下来的情况**：把狗按住不让她走（或者让它面朝墙），推满摇杆，
看本体条带里 `速度` 那一格。**推满摇杆而实际速度是 0，超过 1.5 秒会变琥珀色**
—— 那是在说「它在被要求走但没走」。如果它**闪个不停**，说明持续判定没生效，
要改。

还要试：

- **松开摇杆 / 松开 W** → 应该是斜坡减速，不是急停
- **按 `stop`** → 快速停，状态显示「已停止」（**不是「已急停」**）
- **切换「分控」模式** → 左右两套键分别控两只狗（现在只有一只，看界面反应即可）

## 4. 急停（5 分钟）—— **请谨慎，但请一定测**

上一次真机会话**没测过急停**，而它是最该测的。

1. 让狗慢慢走起来（推一点 W）
2. 按**红色急停**
3. 观察：狗是**立刻阻尼瘫软**，还是滑行一段？

预期控制台侧：状态变「已急停」并**锁存**，摇杆推不动（服务端 409 拒绝）。

然后按「解除急停」→ 状态回到「空闲」，但**狗不会自己站起来** —— 需要点
「站立」或「恢复」。这是设计如此。

**要回答的问题**：急停之后，狗是站着不动还是趴下了？
如果是趴下，那「解除急停」后面应该补一条站立提示。

## 5. 上第二只狗（10 分钟）

**这是完全没测过的部分**（上次只有一只狗在网上）。

| 检查项 | 预期 |
|---|---|

`scripts/measure_connect_interference.py` 就是量这个的，现场跑一次：


## 6. 同步标定 + 配对转向（15 分钟）—— **本轮新增**

**先把两只狗并排摆好，朝同一个方向。** 这一步的假设是**人把它们摆齐了** ——
控制台无法自己知道这件事，所以它不猜。

点舰队栏的**「标记对齐」**。预期提示 `已以 dog1、dog2 为基准`。

然后**一起转 90°**（舰队动作「右转 90°」）。看着两只狗，同时看界面上的
同步行：

```
同步 [同步]  dog1 ↔ dog2  朝向差 0.8°  路程差 0.02 m
```

**要观察的是**：

1. 转完之后**朝向差是多少**？（真机上大概率 3–10°，不是 0）
2. 两只狗**停下的时刻差多少**？（闭环转向，各转各的）
3. 同步行的数字**跟肉眼看到的一致吗**？两只狗看起来差多少度，界面说多少度？

**这一条最重要**：如果界面说「同步」但两只狗肉眼看着明显不齐，那么
**「各自相对基准的变化量」这个测量方法在真机上不够用** —— 那就是要上视觉的
信号，也正是下一步（定位）的价值所在。**请务必把肉眼观察和界面数字都记下来。**

反复转 4 次 90°，看误差是**累积**还是**保持**。

## 7. 编排：走正方形（15 分钟）—— **自动纠正在这里生效**

从舰队栏点**「走正方形 · 9步/32s」**。

预期时间线：

1. **运行前整条 9 步都是「待执行」**（这才叫时间线）
2. 每步一张卡，带策略徽章和**每狗一个点**
3. 第 1 步是**站立** —— 不再第一步就失败

**重点看第 2、4、6、8 步（右转 90°）**。这些步跑完之后，卡片上可能多出一个
**琥珀色的 `已纠正 dog2 +12°`**。那是控制台发现两只狗转得不一样多，
**给落后的那只补了一次不超过 12° 的转向**。

要确认的：

1. 出现过「已纠正」吗？补的方向**对不对**？（补反了会让狗越转越歪）
2. 补完之后，两只狗**看起来更齐了还是更歪了**？
3. **补的时候狗有没有「顿一下」**？两次转向之间的停顿是否可以接受？

不想要自动纠正的话，可以在卡片上看出来它做了什么 —— **它一定会说**，
不会偷偷转你的狗。

## 7.5 空翻参数 —— **一个必须现场判定的事**（5 分钟）

挖掘 wpp 分支时发现的：**我们原来给所有 Go2 运动动作都发 `parameter=None`**，
而库自带的示例里 `Pose` / `FrontFlip` / `LeftFlip` / `BackFlip` 都传
`{"data": True}`（`examples/go2/data_channel/sportmode_mcf/sportmode_mcf.py:193`、
`:229` 是活代码）。

**已经改了**，但证据来自 **MCF 那套 api_id**（`BackFlip` 在那边是 2043，我们发
1044），所以是**强证据不是证明**。

现场只需要按一次：

1. 让狗在**空旷、软地面**上站好
2. 点「前空翻」（会要求确认）
3. 看结果：

| 看到什么 | 说明什么 | 我该做什么 |
|---|---|---|
| **狗翻了** | 参数是对的 | 收工 |
| **狗没反应，工具报 `code: 0`** | 1044 这个 id 不吃 `{"data": True}`，或者压根不支持 | 去掉那一条，改回裸发 |
| **工具报 `code != 0`** | 拒绝了这个带参数的请求 | 去掉那一条，改回裸发 |
| 界面报错说动作不存在 | 名字对不上 | 把报错原样带回来 |

**不要在没有空间的地方试。** 前空翻和后空翻需要落点。

## 7.6 `Move` 的单位 —— **一次测量消除 3.5 倍的歧义**（5 分钟）

**这是最常用的移动原语上的一个未解歧义**，而且仓库里没有答案（库里没有更高层
封装，README 不写单位）。

`robot_move` 发的是 Unitree 的 sport `Move` (1008)：

- **SDK 语义**：x/y 是**米每秒**，z 是**弧度每秒**
- **WebRTC app 协议**：被广泛描述成**归一化杆量**

**两者在 0 处重合，差一个"机器人最高速度" —— Go2 上约 3.5 倍。**

### 怎么问清楚

1. 找**一块空地**，地上标一条线（或者放个明显的东西）
2. 让狗站好，`robot_move(vx=1.0, duration_s=2, confirm=true)`
3. **量它走了多远**

| 走了多远 | 说明 | 我要做什么 |
|---|---|---|
| **约 2 米** | 是**米每秒** | 编队的横向修正会慢 3 倍 —— 把 `NOMINAL_MAX_SPEED_MPS` 改成 1.0 |
| **约 6–7 米** | 是**归一化** | 现在的假设是对的，收工 |

**钳制值 1.0 在两种读法下都安全**（要么 1 m/s，要么满速），所以这**不是安全
问题，是精度问题**。

### 如果它真的是米/秒，会看到什么

**编队报 `no_progress` 然后停下。** 步历史显示修正缩得太慢（每步只走预期的
三分之一），而没有任何东西说明原因 —— 一个单位 bug 从外面看就长这样。
前进修正现在优先走 `robot_walk`（摇杆路径，**没有这个歧义**），所以受影响的是
横向和转向。

## 7.8 停不下来的情况 —— **必须测，而且要小心测**（10 分钟）

这一条是本轮**修掉的一个真安全 bug**：看门狗清零了斜坡的内部值，**却一帧都没发出去**，
机器人继续执行收到的最后一帧。在 `rt/wirelesscontroller` 上那就是**一直走**。

（我在 wpp 分支里看到这个失效模式，回来想写个测试证明我们没这个问题 —— **测试挂了**。）

已修，但**必须在真机上确认**。测法：

1. **空旷场地**，狗站好，慢慢推 W 让它走起来（小速度，别快）
2. 松开 W → 应该是**斜坡减速**停下，不是急停
3. 再走起来，然后**切换到别的窗口**（alt-tab / cmd-tab）
4. 观察：狗应该**在约 0.5 秒内停下**

**第 4 步是关键。** 预期是"停"，因为看门狗跑在**服务端**，不依赖浏览器。

**如果狗继续走**：立刻按急停，然后**记下细节** —— 是松开了键还是切了窗口、走了多久、
界面上驱动状态显示什么。这是我改动的核心，错了要马上改。

**更狠的版本**（愿意就测）：走起来之后**直接关掉浏览器标签页**。狗应在 0.5 秒内停。

## 8. 长时间开着（20 分钟以上）

把控制台开着，两只狗连着，**让它跑几轮编排**，然后放着。

20 分钟后检查：

- 浏览器**内存**有没有明显涨（开发者工具 → Memory）
- 视频**有没有断**，断了会不会自愈
- 两只狗**还连着吗**（租约不该把它们放掉）
- 编排跑完之后，狗是不是**好好停着**

```sh
grep -c "ERROR\|Traceback" /tmp/console.log     # 预期 0
grep -i "released\|lease" /tmp/console.log      # 狗不该被租约放掉
```

## 9. 出问题怎么办 —— 症状对照表

**先记下症状，再动手。** 现场最贵的不是修，是**丢失现场信息**。

| 症状 | 最可能的原因 | 现场处置 |
|---|---|---|
| 按 W 狗不动，状态一直是「等待站立…」 | 站立命令被拒（可能急停锁存、或狗在阻尼态） | 看锁存指示灯；点「站立」看返回什么 |
| 状态「等待站立…」然后就「站立超时」 | 超过 5 秒没站起来 | 狗可能被卡住或者电池低；看狗本身 |
| 按 W 完全没反应，状态停在「空闲」 | **键盘焦点不在控制台**，或者按了「分控」但焦点在另一只 | 点一下页面再按；看舰队栏的焦点标记 |
| 摇杆动但狗不动 | 狗没站好 / 避障开关开着 | 看本体条带的琥珀色卡住提示 |
| 视频黑屏但有电量 | MJPEG 流卡了 | 点狗卡片上的「画面」开关重开 |
| 连第二只时第一只卡住 | 事件循环被握手阻塞 | 跑 `measure_connect_interference.py` |
| 遥控被官方 App 抢走 | 一个机器人只有一个 WebRTC 槽位 | 关掉 App；控制台会显示 `RobotBusyError` |
| 编排中途停了 | 急停锁存 / 某步策略是 `all` 但有狗失败 | 看时间线哪张卡是红的，每狗的点说明是哪只 |
| **按了动作/空翻，狗完全没反应，也没报错** | `parameter` 不对（见第 7.5 节） | 看工具返回的 `code`；把动作名和 code 带回来 |
| **松开 W / 切走窗口之后狗还在走** | 看门狗没把零帧发出去（`fee57e0` 修的就是这个） | **立刻按急停**，然后记下：当时是松开了、还是切走了窗口 |
| 同步行说「无法判断」 | 狗没发布 `position` | 这就是探针第 1 步要看的东西 |

**任何一种情况**：截图 + 控制台日志 + 当时的界面数字，带回来。

## 附二：视觉定位（下一步，不用等实机）

状态机级别的同步已经做完了，**这是你一直想做的视觉定位的第一步：可打印的标记**。

```sh
.venv/bin/python -c "
from pathlib import Path
from unitree_robot_agent.vision import default_markers, write_markers
write_markers(Path('/tmp/markers'), default_markers(['dog1','dog2']))
"
```

生成 `docs/markers/tag_0_dog1_print.png` 和 `tag_1_dog2_print.png` —— **每张一页 A4，200×257mm**。

**打印时要做的两件事：**

1. **按 100% 打印，不要「适合页面」。** 黑方块必须是 **150mm**，打完拿尺子量一下。
   打小了不会报错，只会读不到 —— 看起来像检测器的 bug。
2. **贴的时候让箭头指向狗头。** 贴歪 90° 就会报出歪 90° 的朝向，
   **检测本身永远不会告诉你贴错了**。

### 需要什么相机（实测的数字，不是口诀）

| 相机 | 60° 视角 | 90° 视角 |
|---|---|---|
| 720p | 2.6 m | 1.5 m |
| 1080p | **3.9 m** | 2.3 m |
| 1440p | 5.2 m | 3.0 m |
| 4K | 7.8 m | 4.5 m |

**一张 1080p 的普通摄像头，在 4 米以内够用。** 想在 5 米外读，需要 2464px 以上的宽度。

### 为什么这次能解决"两只狗各有各的原点"

里程计不行 —— 我之前记录过：两只狗的 `position` 各自相对于**各自估计器启动的地方**，
所以同步模块只能测"它们动得有多不一样"，永远测不出"它们在哪"。

**一台相机同时看两只，就没有这个问题：一帧、一个坐标系、两只都在里面。**
这也是标记要贴在**背上**的原因 —— 狗看不见自己的背，相机必须是**第三个**在看的角色。

### 检测已经能跑（不用等实机）

```sh
.venv/bin/python scripts/vision_demo.py --simulate /tmp/arena.png
```

会画出两只狗在已知位置、再读回来、把**读到的和画出来的并排打印**：

```
狗                      画在                 读回       误差
dog1   ( 1.00, 2.00,   0.0°) ( 1.00, 2.00,   0.0°)   0.004m
dog2   ( 3.00, 2.00, 180.0°) ( 3.00, 2.00, 180.0°)   0.004m
间距 1.994 m   朝向差 180.0°
```

**误差 4 毫米。** 这条命令在两个会话之间也能验证整条链路有没有坏。

### ⚠️ 标定靶要放在**狗背的高度**，不要放地上

这是本轮最重要的发现，而且是**量出来的**：

标记在狗背上、离地约 35cm。**用地板标定的单应性**报到的是"看向标记的视线与地板相交的点"，
误差是一个**以相机正下方为中心的径向放大**，倍数 = `H/(H-h)`：

| 相机高度 | 4 米场地最坏绝对误差 | 两只狗相距 1 米会读成 |
|---|---|---|
| 1.5 m | 0.66 m | 1.30 m |
| 2.5 m | 0.40 m | 1.16 m |
| 4.0 m | 0.25 m | 1.11 m |
| 8.0 m | 0.12 m | 1.05 m |

**即使把相机架到 8 米高，也超不过"半个狗宽"那条线。**

这不是放弃的理由 —— **两只狗被同一个倍数放大，所以形状是对的、尺寸是错的**。
但这正是**要把标定靶垫到狗背高度**的理由：那样误差**从构造上就是 0**。

**操作上就是**：找两个和狗背差不多高的箱子，把四个标定点放在上面量，
而不是贴在地上量。`Calibration.adequate` 会告诉你当前是哪种情况。

### ⚠️ 这一轮修掉的：命令发给了错误的狗

**2026-10 会话中发现**：`call_tool("dog2", "robot_walk")` 报告 `robot_id: dog2`、
`ok: true` —— 而**动的是 dog1**，dog2 原地不动。

根因：`ToolContext` 里跟随 `robot_id` 绑定的委托只有 `config`/`profile`/`session`/
`audit`/`backend`，而工具直接写 `ctx.runtime.motion` —— **`ctx.runtime` 是注册时
捕获的默认那只狗，从不重绑**。响应由 `ok()` 构造，用的是当前绑定的 robot_id，所以
**它报告你点的那只，同时驱动另一只**。

受影响的四个族：**运动（move/turn/walk）、故障、密钥、视觉（拍照）**。

**真机实测时请特别验证这一条**：控制台点 dog2 的"前进"，确认**只有 dog2 动**。

### 编队：填目标，点对齐

场地视图里有一行**编队**：

```
编队  目标间距 [1.0] 米  方位 [0]°  朝向差 [0]°  [两只一起挪 ▾]   [对齐]
```

点「对齐」之后它会**一步步来**，每走一步重新量一次，并排显示每一次的测量：

```
间距 1.800 m（+0.800）  间距 1.575 m（+0.575）  间距 1.356 m（+0.356）  间距 1.138 m（+0.138）
```

绿色是到位、琥珀色是还差。

**它会自己停，而且告诉你为什么：**

| 停法 | 意思 |
|---|---|
| `已到位` | 达标 |
| `没有进展` | 误差不再变小 —— **再走也修不好一个错的常数** |
| `测不到位置` | 狗出画或相机停更 —— **从过期位置继续开就是盲开** |
| `步数用完` | 超出预算 |
| `急停中止` | 锁存了 |

**射程约一米。** 归一化速度换算之后一步实际走 **0.22 米**（实测），默认六步。这是给"两只狗大致到位了"的修正，**不是让它们穿过房间**。差距更大就先手动开近一点。
