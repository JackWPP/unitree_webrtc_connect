# 真机会话脚本 —— 双狗实测

给现场用。按顺序做，每步都有**预期结果**和**不对时怎么判断**。

上一次真机会话（单狗）的结论在 [HARDWARE_BRINGUP.md](HARDWARE_BRINGUP.md)
的「First real session」。那份文档回答的是"能不能连上"，这份回答的是
"**两个一起能不能用**"。

## 1. 探针 —— 全场最重要的一条命令（2 分钟）

**先做这个。** 它决定后面能做什么，而且它是只读的，不会占用控制权。

```sh
.venv/bin/python scripts/probe_webrtc_topics.py \
    --ip 192.168.31.188 --sn B42N6000Q3UC1M8C
```

会打印一张 13 行的表。**上次的结果**：`lowstate` / `multiplestate` 应答，
**`rt/sportmodestate` 静默 8 秒**（站起来之后也一样）。

这次要特别看三行：

| 行 | 有数据意味着 | 静默意味着 |
|---|---|---|
| `rt/lf/sportmodestate` | **步态/模式有了** —— 控制台现在能显示它 | 维持现状：控制台不显示步态，且**不假装** |
| `rt/utlidar/robot_pose` | **绝对位姿有了** —— 可以做真实地图和编队 | 「在哪」只能到"位移+朝向" |
| `rt/mapping/grid_map` | 可以做占用栅格图 | 不做 |

`--json` 出机器可读的版本，**原样带回来**。

> **看到静默不要当成故障。** 固件就是不在 WebRTC 上发它。这是本项目的核心
> 纪律：**没有第二条路拿到数据之前，不在静默的行上建功能。**

## 2. 单狗接管（5 分钟）

**先准备 roster。** 控制台不知道狗在哪，必须先告诉它 —— 而且**两只狗的 roster
要一起写好**，第 5 步就不用再回头改：

```sh
cat > /tmp/dogs.json <<'JSON'
{
  "default": "dog1",
  "state_dir": "/tmp/unitree-console",
  "robots": [
    {"id": "dog1", "model": "Go2", "ip": "192.168.31.188", "sn": "B42N6000Q3UC1M8C"},
    {"id": "dog2", "model": "Go2", "ip": "192.168.31.XXX", "sn": "第二只的SN"}
  ]
}
JSON
export UNITREE_AGENT_ROSTER=/tmp/dogs.json
```

**第二只的 IP 和 SN 要从路由器后台或者狗身上的标签拿。** 上次会话时它不在网上，
所以这个值我没有。

然后**只读体检**（不占用狗的 WebRTC 槽位，可以放心跑）：

```sh
.venv/bin/python -m unitree_fleet_web.cli --preflight
```

预期每只狗一行 `[OK]`。上次的真实输出长这样：

```
[OK]   dog1     Go2  192.168.31.188   ready, data2=3
```

不通的时候它会**说清楚是哪一步不通**：

```
[FAIL] dog1     Go2  192.168.31.188   unreachable
         no answer on 9991 or 8081
         → Neither signaling port answered. Check the robot is powered on and
           on this network, and that no firewall is blocking 9991/8081.
```

起控制台：

```sh
.venv/bin/python -m unitree_fleet_web.cli --port 8080 --log-level INFO 2>&1 | tee /tmp/console.log
# 浏览器打开 http://127.0.0.1:8080
```

点狗卡片上的「连接」。预期：

- **视频**：1280×720，约 4 fps，真切画面
- **电量条**：94–98%，32 V 左右
- **本体条带**：姿态气泡居中、四根足端柱、`速度 0.00 m/s　指令 0.00`
- **感知页的数据来源清单**：`电量/IMU/足端`、`音量/亮度/避障开关` 亮**有数据**

**如果步态那一行是「未应答」** —— 那是已知情况（探针第 1 步会确认），不是坏了。

## 3. 驾驶 —— 站立闸门第一次上真机（10 分钟）

这是本轮改动里**最需要真机验证**的一条。

**先让狗趴下**（姿态页点「趴下」），等它趴稳。然后**按 W**。

预期看到驱动状态依次是：

```
空闲  →  等待站立…  →  行驶中
```

**「等待站立…」是关键。** 它意味着控制台发现狗没站好，**先发了一条站立命令，
并且没有下发速度**。上真机之前它只会是：按 W，什么都不发生，也没有解释。

要确认的：

1. 「等待站立…」大约持续多久才变成「行驶中」？（真机大概 1–2 秒）
2. 狗**站起来之后**才走，还是**一边起身一边走**？后者是 bug。
3. 直接对已经站着的狗按 W，**不该**出现「等待站立…」。

再试**停不下来的情况**：把狗按住不让她走（或者让它面朝墙），推满摇杆，
看本体条带里 `速度` 那一格。**推满摇杆而实际速度是 0，超过 1.5 秒会变琥珀色**
—— 那是在说「它在被要求走但没走」。如果它**闪个不停**，说明持续判定没生效，
要改。

还要试：

- **松开摇杆 / 松开 W** → 应该是斜坡减速，不是急停
- **按 `stop`** → 快速停，状态显示「已停止」（**不是「已急停」**）
- **切换「分控」模式** → 左右两套键分别控两只狗（现在只有一只，看界面反应即可）

## 4. 急停（5 分钟）—— **请谨慎，但请一定测**

上一次真机会话**没测过急停**，而它是最该测的。

1. 让狗慢慢走起来（推一点 W）
2. 按**红色急停**
3. 观察：狗是**立刻阻尼瘫软**，还是滑行一段？

预期控制台侧：状态变「已急停」并**锁存**，摇杆推不动（服务端 409 拒绝）。

然后按「解除急停」→ 状态回到「空闲」，但**狗不会自己站起来** —— 需要点
「站立」或「恢复」。这是设计如此。

**要回答的问题**：急停之后，狗是站着不动还是趴下了？
如果是趴下，那「解除急停」后面应该补一条站立提示。

## 5. 上第二只狗（10 分钟）

**这是完全没测过的部分**（上次只有一只狗在网上）。

连上第二只之后要看：

| 检查项 | 预期 |
|---|---|
| 两条视频流 | 都出画面，互不干扰 |
| 两只狗的电量/姿态 | 各自独立，不串 |
| **连接第二只时，第一只卡不卡** | 不应卡（事件循环不应被握手阻塞） |
| 「全部」模式按 W | **两只一起走**，出发间隔看不出来 |
| 「分控」模式 | 各按各的键 |

如果**连第二只的时候第一只的视频卡住**，那是事件循环被阻塞 ——
`scripts/measure_connect_interference.py` 就是量这个的，现场跑一次：

```sh
.venv/bin/python scripts/measure_connect_interference.py --help
```

## 6. 同步标定 + 配对转向（15 分钟）—— **本轮新增**

**先把两只狗并排摆好，朝同一个方向。** 这一步的假设是**人把它们摆齐了** ——
控制台无法自己知道这件事，所以它不猜。

点舰队栏的**「标记对齐」**。预期提示 `已以 dog1、dog2 为基准`。

然后**一起转 90°**（舰队动作「右转 90°」）。看着两只狗，同时看界面上的
同步行：

```
同步 [同步]  dog1 ↔ dog2  朝向差 0.8°  路程差 0.02 m
```

**要观察的是**：

1. 转完之后**朝向差是多少**？（真机上大概率 3–10°，不是 0）
2. 两只狗**停下的时刻差多少**？（闭环转向，各转各的）
3. 同步行的数字**跟肉眼看到的一致吗**？两只狗看起来差多少度，界面说多少度？

**这一条最重要**：如果界面说「同步」但两只狗肉眼看着明显不齐，那么
**「各自相对基准的变化量」这个测量方法在真机上不够用** —— 那就是要上视觉的
信号，也正是下一步（定位）的价值所在。**请务必把肉眼观察和界面数字都记下来。**

反复转 4 次 90°，看误差是**累积**还是**保持**。

## 7. 编排：走正方形（15 分钟）—— **自动纠正在这里生效**

从舰队栏点**「走正方形 · 9步/32s」**。

预期时间线：

1. **运行前整条 9 步都是「待执行」**（这才叫时间线）
2. 每步一张卡，带策略徽章和**每狗一个点**
3. 第 1 步是**站立** —— 不再第一步就失败

**重点看第 2、4、6、8 步（右转 90°）**。这些步跑完之后，卡片上可能多出一个
**琥珀色的 `已纠正 dog2 +12°`**。那是控制台发现两只狗转得不一样多，
**给落后的那只补了一次不超过 12° 的转向**。

要确认的：

1. 出现过「已纠正」吗？补的方向**对不对**？（补反了会让狗越转越歪）
2. 补完之后，两只狗**看起来更齐了还是更歪了**？
3. **补的时候狗有没有「顿一下」**？两次转向之间的停顿是否可以接受？

不想要自动纠正的话，可以在卡片上看出来它做了什么 —— **它一定会说**，
不会偷偷转你的狗。

## 7.5 空翻参数 —— **一个必须现场判定的事**（5 分钟）

挖掘 wpp 分支时发现的：**我们原来给所有 Go2 运动动作都发 `parameter=None`**，
而库自带的示例里 `Pose` / `FrontFlip` / `LeftFlip` / `BackFlip` 都传
`{"data": True}`（`examples/go2/data_channel/sportmode_mcf/sportmode_mcf.py:193`、
`:229` 是活代码）。

**已经改了**，但证据来自 **MCF 那套 api_id**（`BackFlip` 在那边是 2043，我们发
1044），所以是**强证据不是证明**。

现场只需要按一次：

1. 让狗在**空旷、软地面**上站好
2. 点「前空翻」（会要求确认）
3. 看结果：

| 看到什么 | 说明什么 | 我该做什么 |
|---|---|---|
| **狗翻了** | 参数是对的 | 收工 |
| **狗没反应，工具报 `code: 0`** | 1044 这个 id 不吃 `{"data": True}`，或者压根不支持 | 去掉那一条，改回裸发 |
| **工具报 `code != 0`** | 拒绝了这个带参数的请求 | 去掉那一条，改回裸发 |
| 界面报错说动作不存在 | 名字对不上 | 把报错原样带回来 |

**不要在没有空间的地方试。** 前空翻和后空翻需要落点。

## 7.8 停不下来的情况 —— **必须测，而且要小心测**（10 分钟）

这一条是本轮**修掉的一个真安全 bug**：看门狗清零了斜坡的内部值，**却一帧都没发出去**，
机器人继续执行收到的最后一帧。在 `rt/wirelesscontroller` 上那就是**一直走**。

（我在 wpp 分支里看到这个失效模式，回来想写个测试证明我们没这个问题 —— **测试挂了**。）

已修，但**必须在真机上确认**。测法：

1. **空旷场地**，狗站好，慢慢推 W 让它走起来（小速度，别快）
2. 松开 W → 应该是**斜坡减速**停下，不是急停
3. 再走起来，然后**切换到别的窗口**（alt-tab / cmd-tab）
4. 观察：狗应该**在约 0.5 秒内停下**

**第 4 步是关键。** 预期是"停"，因为看门狗跑在**服务端**，不依赖浏览器。

**如果狗继续走**：立刻按急停，然后**记下细节** —— 是松开了键还是切了窗口、走了多久、
界面上驱动状态显示什么。这是我改动的核心，错了要马上改。

**更狠的版本**（愿意就测）：走起来之后**直接关掉浏览器标签页**。狗应在 0.5 秒内停。

## 8. 长时间开着（20 分钟以上）

把控制台开着，两只狗连着，**让它跑几轮编排**，然后放着。

20 分钟后检查：

- 浏览器**内存**有没有明显涨（开发者工具 → Memory）
- 视频**有没有断**，断了会不会自愈
- 两只狗**还连着吗**（租约不该把它们放掉）
- 编排跑完之后，狗是不是**好好停着**

```sh
grep -c "ERROR\|Traceback" /tmp/console.log     # 预期 0
grep -i "released\|lease" /tmp/console.log      # 狗不该被租约放掉
```

## 9. 出问题怎么办 —— 症状对照表

**先记下症状，再动手。** 现场最贵的不是修，是**丢失现场信息**。

| 症状 | 最可能的原因 | 现场处置 |
|---|---|---|
| 按 W 狗不动，状态一直是「等待站立…」 | 站立命令被拒（可能急停锁存、或狗在阻尼态） | 看锁存指示灯；点「站立」看返回什么 |
| 状态「等待站立…」然后就「站立超时」 | 超过 5 秒没站起来 | 狗可能被卡住或者电池低；看狗本身 |
| 按 W 完全没反应，状态停在「空闲」 | **键盘焦点不在控制台**，或者按了「分控」但焦点在另一只 | 点一下页面再按；看舰队栏的焦点标记 |
| 摇杆动但狗不动 | 狗没站好 / 避障开关开着 | 看本体条带的琥珀色卡住提示 |
| 视频黑屏但有电量 | MJPEG 流卡了 | 点狗卡片上的「画面」开关重开 |
| 连第二只时第一只卡住 | 事件循环被握手阻塞 | 跑 `measure_connect_interference.py` |
| 遥控被官方 App 抢走 | 一个机器人只有一个 WebRTC 槽位 | 关掉 App；控制台会显示 `RobotBusyError` |
| 编排中途停了 | 急停锁存 / 某步策略是 `all` 但有狗失败 | 看时间线哪张卡是红的，每狗的点说明是哪只 |
| **按了动作/空翻，狗完全没反应，也没报错** | `parameter` 不对（见第 7.5 节） | 看工具返回的 `code`；把动作名和 code 带回来 |
| **松开 W / 切走窗口之后狗还在走** | 看门狗没把零帧发出去（`fee57e0` 修的就是这个） | **立刻按急停**，然后记下：当时是松开了、还是切走了窗口 |
| 同步行说「无法判断」 | 狗没发布 `position` | 这就是探针第 1 步要看的东西 |

**任何一种情况**：截图 + 控制台日志 + 当时的界面数字，带回来。

## 10. 要带回来的东西（按重要性）

1. **探针的 `--json` 输出** —— 决定后面所有功能能不能做
2. **同步标定那一节：界面数字 vs 肉眼观察** —— 决定要不要上视觉
3. **站立闸门那一节**：从按 W 到狗动起来，实际多久；中间有没有"边起边走"
4. **急停**：狗是瘫软还是滑行；解除之后是什么姿态
5. **双狗时序**：连第二只时第一只卡不卡；两只一起走的出发间隔肉眼看得出来吗
6. **走正方形的「已纠正」**：出现过吗，方向对不对，狗看起来更齐还是更歪
7. 任何**和文档描述不一样**的地方 —— 尤其是"界面说 A，狗实际是 B"

## 附：本轮为了真机做的改动，都是**没在真机上跑过**的

诚实清单。这些在 mock 上有测试，但 mock 不是狗：

- **站立闸门**：从"控制台自己发过的命令"推断姿态。官方 App 动过狗、或者狗摔了，
  推断就是错的。**这是最需要真机验证的一条。**
- **同步标定**：测量方法是「各自相对基准的变化量」，假设是**人把它们摆齐了**。
- **自动纠正**：一次、封顶 12°。真机上补得对不对、会不会显得突兀，没验证过。
- **本体条带**：姿态/足端/速度的阈值（12°/25° 倾斜、1.5 秒卡住）都是拍的，
  真机上可能要调。
- **急停**：上一次真机会话没测过。
- **双狗并发**：完全没测过。
